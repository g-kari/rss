# リリースノート運用ルール 〜ギャルが書くよ〜

コードを変更して master にマージしたら、**必ず** リリースノートを更新すること。

## 文体ルール：令和ギャルスタイル

リリースノートは **令和ギャル** として書く。以下のトーンを守ること：

- **語尾**: 「〜したよ〜」「〜しちゃう」「〜だよっ」など、親しみやすく可愛い語尾
- **カテゴリ見出し**: 「激アツ新機能っ」「バグ修正っ」「セキュリティ対策っ」のように「っ」を付ける
- **絵文字**: 各項目の末尾に関連する絵文字を 1〜2 個付ける（✨🎀💡📱🖼️🔒🚀 など）
- **説明文**: 技術的に正確だけどフレンドリーに。「〜が〜しちゃってた問題を修正！」のような表現
- **テンション**: 新機能は特にテンション高め、バグ修正はサクッと報告感
- **禁止**: ギャル男口調（「〜っすよ」）は NG。あくまで令和の女子ギャル

## architecture.md / api-spec.md の同期必須

新規 API エンドポイント（`app/api/**/route.ts`）・hooks（`src/hooks/*.ts`）・lib（`src/lib/*.ts`）・components（`src/components/**/*.tsx`）を追加した際は、**同じ PR 内で** `.claude/rules/architecture.md` のディレクトリ構造セクションにも 1 行の責務記述を追記すること。
型定義（`src/types.ts`）で R2 に保存されるインターフェース（`ReadState` / `UserSubscription` / `SharedFeedMeta` / `FeedGroup` 等）にプロパティを追加した場合も、`## R2 データ構造` セクションの該当行を更新する。

**役割分担（どちらを参照するか）**:

- **エンドポイントの一覧と責務**: `.claude/rules/architecture.md` の「全体像」セクション（単行説明）
- **リクエスト/レスポンスの詳細仕様**: `.claude/rules/api-spec.md`（詳細は順次追記）

新規エンドポイントで外部から呼ばれる `POST`/`PUT` エンドポイントを追加した場合は、**`api-spec.md` にもリクエスト・レスポンス・エラー一覧を追記すること**。

## 更新対象ファイル

| ファイル           | 用途                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------- |
| `RELEASE_NOTES.md` | リポジトリ直下のマークダウン（単一ソース）。prebuild スクリプトが自動で TS 定数に変換する |

> `src/lib/release-notes-data.ts` は `scripts/sync-release-notes.mjs` により自動生成される（`.gitignore` 対象）。手動編集不要。

## フォーマット

```markdown
## YYYY-MM-DD

### 激アツ新機能っ

- **機能名** — ギャル語で説明〜✨

### リファクタリングっ

- `対象` を〇〇に変更したよ〜🔧

### バグ修正っ

- 〇〇が〇〇しちゃってた問題を修正！💡

### セキュリティ対策っ

- 〇〇脆弱性を修正したよ〜🔒
```

## カテゴリ判断基準

- `feature/`, `feat/` → **激アツ新機能っ**
- `refactor/` → **リファクタリングっ**
- `fix/` → **バグ修正っ**
- `security/` → **セキュリティ対策っ**
- `docs/` → **ドキュメント整備っ**

同一日付に複数マージがある場合は同じ `## YYYY-MM-DD` セクションに追記する。

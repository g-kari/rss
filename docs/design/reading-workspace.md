# RSS Reader のUI/UX設計方針

作成日: 2026-10-09。対象: g-kari/rss、変更前UIソース 0fd6874e7d1dde0c6c7c9d3f472c7bb63c31740f。

## こうあるべき

RSSリーダーは、購読先を選び、読む記事を見つけ、本文に集中するための道具。機能の数より、「いまどこを見ているか」「何に絞り込まれているか」「次に何ができるか」をすぐ理解できることを優先する。

- 左: どこを読むか。読む場所、保存した記事、購読先を選ぶ
- 中央: どの記事を読むか。選択範囲、件数、検索、未読、絞り込みを扱う
- 右: 記事を読む。本文を主役にし、記事の保存・メモと読書補助を整理する
- 管理: 設定、入出力、統計、通知、フィードの状態は必要なときに開く

「揃える・まとめる・繰り返す」とOOUIを基礎にする。記事、購読フィード、グループ、コレクションを意味のある対象として扱い、対象への操作と一覧全体への操作を混在させない。

## 利用目的と優先順位

1. 新着を流し読みし、読みたい記事を選ぶ
2. 本文を読み、元記事・全文・要約・翻訳・読み上げを必要に応じて使う
3. ブックマーク、後で読む、いいね、メモ、タグ、コレクションで残す
4. 購読先や表示・自動処理の設定を管理する

画像、動画、SNS、ビジュアル表示、没入型表示も、この目的に沿った既存の読み方として維持する。通常表示の刷新に、新しいメディア処理や自動再生仕様を混ぜない。

## 現状の根拠と判定の限界

READMEと設計ルールでは、3ペイン、フラットで静かな表示、日本語を含む本文、既読同期、5種類の一覧、キーボード操作が製品の基礎として定義されている。

ソースで確認:

- article-list-header/index.tsx:33–73 は、5種のレイアウト・フォーカス・多数のフィルターを横一列に並べる
- FilterPills.tsx:77以降には、未読・ブックマーク・後で読む・いいね・メモ・ダイジェスト・日付・読了時間・カテゴリ・ソート・キーワード・一括既読が並ぶ
- 中央見出しは選択した購読先にかかわらず「記事」になっている
- feed-sidebar/index.tsx:515–609 は、保存系ビューと統計・推薦を購読先より先に置く
- ArticleHeader.tsx は、保存系と読書補助を同じアクション行に合成する

画面で確認した公開デモの一時表示では、中央の操作が横スクロール領域へ切れていた。ただしデモから通常画面への既存遷移があり、確実な合成データの比較証拠には使用しない。

この文書のレイアウト提案は、実コンポーネントをクラウドのChromiumで描画した変更前・変更後の画面と操作を見て最終決定する。コードの宣言だけで「見やすい」「モバイル対応済み」「アクセシブル」とは判定しない。

## 情報設計

### 左のナビゲーション

「読む」: すべて、ダイジェスト。
「ライブラリ」: 後で読む、ブックマーク、いいね、履歴、タグ、コレクション。
「購読フィード」: ピン留め、グループ、カテゴリ、その他の購読先。

購読先検索と記事・画像・動画・SNSの切り替えは常に見つかる位置に残す。統計・関連フィード推薦は購読先を押し下げない補助領域にまとめる。既存の追加、更新、URL保存、フッターメニューへの入口を保つ。

### 中央の一覧

上から、選択範囲と件数、検索、一覧操作、記事の順。
未読は日常の絞り込みとして文字付きで常時表示。その他の条件は「絞り込み」からラベル付きで開く。選択中の条件を件数・短い要約で外側にも表示し、検索結果ゼロを「記事がない」と取り違えないようにする。
表示方法は「表示」で5種類と一覧フォーカスを選ぶ。並び順と一括既読は一覧全体への操作として、フィルターとはグループを分ける。既存の確認とUndoはそのまま使う。

### 右の本文

記事の出典・日時・著者を本文の前にまとめる。「保存・整理」と「読むための補助」を別の操作群にする。保存状態、メモの下書き、進行中の取得・要約・翻訳・音声再生を失わない。狭いペインでも操作群を折り返し、本文を覆う新たな固定バーは作らない。

## 見た目と操作の原則

- 既存の面の階層 surface-nav → surface-base → surface-elevated を使う
- 配色はセマンティックトークンを再利用。アクセントは現在地・主操作。未読、保存、エラーの意味色を維持
- UIは既存のReddit Sans + IBM Plex Sans JPと用途別の文字サイズ。本文のサイズ・行間・幅設定を維持
- 余白は既存のスケールを使い、同じ対象と操作を近づけ、別の操作群は離す
- 現在地と未読は色だけでなく側線、下線、ドット、文字の太さ、ARIAで区別
- 頻繁な操作を謎のアイコンへ隠さない。名称は同じ操作で同じ語を使う
- 演出は既存のモード設定とreduced-motionに従う。本文の表示を待たせない

## モバイル・キーボード・アクセシビリティ

スマホでは、ナビ → 一覧 → 本文の1ペインずつの移動を維持する。戻る、ブラウザーのBack/Forward、一覧位置、選択記事、モーダルのキャンセル・繰り返し操作を実際に確認する。
主要操作はタップ領域44pxを目標にし、320px・390pxの実viewportで横切れを確認する。キーボードは既存のj/k、n/p、検索、保存、既読、ヘルプ等を変えない。ダイアログは既存のフォーカストラップとEscape・元の操作へのフォーカス復帰を使う。
200%文字拡大、長い日本語・英語混在タイトル、light/dark、キーボードfocus、reduced-motion、forced-colorsを対象にする。ARIAがあるだけでスクリーンリーダーの実機検証を済ませたとは扱わない。

## 受入条件

1. 同じ実コンポーネント・本番CSS・合成データを使い、変更前と最終headのPC/スマホのPNGを比較する
2. 通常状態の一覧ヘッダーで、320/390pxと360/420pxの一覧ペインに必要な操作が収まり、横スクロールしない
3. 選択したフィード・グループ・タグ・コレクション・特殊ビューの見出しが中央に一致する
4. 絞り込みと表示設定の全項目に文字ラベルがあり、開く・適用・閉じる・Escape・フォーカス復帰が動く
5. 有効な条件が一覧の外側にもわかり、既存の条件解除・検索・並び順・一括既読の結果が維持される
6. 既読/未読、保存、後で読む、メモ、購読先、画像/動画/SNS、通常/ビジュアル/没入型表示が回帰しない
7. loading、empty、error/retry、offline、未同期状態、長文、一覧の多数件・仮想化を確認する
8. 最終差分でpnpm check、typecheck、unit、関連Chromium fixture、既存aggregate CIを実行する。未実行をpassとしない

## 実装・展開・戻し方

UIのPRは、Serena指定の撤廃PR、Codex/文書整備PRと別にする。このUI差分はナビゲーション・一覧操作・本文操作群・その回帰テストに限定する。認証、課金、データ構造、API、外部公開範囲、ユーザーの設定値を変えない。
まずdraftで比較画像と検証結果を提示する。マージと本番反映は既存の承認条件・保留を守る。問題が見つかった場合はUI commitのrevertで戻せる構成にし、データの巻き戻しを必要としない。

## デザイン資料の由来

使用したデザイン資料は、既に接続されているFront-end Design（Anthropic由来のApache-2.0適応版）、Impeccable v4.5のApache-2.0による指示文の適応版、Vercel Web Interface GuidelinesのMITによるレビュー基準。実行エンジンや有料APIではなく、設計と手動レビューの資料として使用する。
新しいランタイム、外部フォント配信、アイコンライブラリ、画像アセット、フレームワークは導入しない。
